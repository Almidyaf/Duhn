# البنية التقنية وحفظ البيانات وجلبها

هذه مواصفة البنية العامة؛ نُفذ أساس التطبيق وPostgreSQL المحلي وإدارة الأصول والكتالوج ومسودات الوصفات والاستلام ودفتر الخام. لا توجد بيئة منشورة أو بيانات مصنع حقيقية. الحالة الدقيقة في [PROGRESS.md](PROGRESS.md)، وعقد المواد التالي في [MATERIAL-CONTRACT.md](MATERIAL-CONTRACT.md).

## 1. بنية محدودة الخدمات

| الطبقة | الاختيار المقترح | الغرض |
|---|---|---|
| تطبيق الويب والخادم | Next.js App Router + TypeScript | واجهة عربية وخدمات أعمال في مستودع واحد |
| قاعدة البيانات | PostgreSQL بإصدار مستقر مدعوم | المعاملات، القيود، الأرصدة والتتبع |
| الوصول للبيانات | node-postgres، SQL بمعاملات وقيم parameterized | مسار واضح للأقفال والحركات دون ORM إضافي |
| المصادقة | Better Auth مع مخزن جلسات PostgreSQL | إدارة تسجيل الدخول والجلسات؛ التفويض التجاري داخل خدمات المشروع |
| تحقق المدخلات | Zod بعقود مشتركة للحدود | التحقق على الخادم والواجهة دون تكرار قواعد العمل |
| تحديث شاشة العميل | SWR | إزالة الجلب المكرر وتحديث عند الرجوع أو الاتصال |
| المهام الخلفية | Node worker من المستودع نفسه + جداول مهام PostgreSQL | إشعارات دائمة تعمل دون متصفح |
| الاختبارات | Vitest + PostgreSQL للاختبار + Playwright | قواعد، معاملات، ورحلات متصفح |
| المرفقات إن فُعلت | تخزين كائنات خاص | حفظ الملفات خارج صفوف قاعدة البيانات |

لا حاجة مبدئية إلى Redis أو Kubernetes أو microservices أو Elasticsearch. المكونات الحالية تُوسع بعد القياس. خدمة الويب والعامل الخلفي عمليتان مستقلتان قابلة لإعادة التشغيل؛ تشتركان في منطق الأعمال وقاعدة البيانات.

Next.js يوصي بطبقة وصول خادمية تفحص الصلاحيات وتعيد بيانات محدودة؛ نعتمد هذه القاعدة ولا نضع استعلامات عشوائية داخل مكونات العرض. [مرجع حماية البيانات](https://nextjs.org/docs/app/guides/data-security).

## 2. هيكل مقترح للمستودع بعد التأسيس

    src/app/                 الصفحات وroute handlers الرفيعة
    src/components/          مكونات واجهة مشتركة
    src/features/            واجهات كل مجال
    src/server/auth/         الجلسات والتفويض
    src/server/services/     قواعد الأعمال والمعاملات
    src/server/repositories/ استعلامات SQL
    src/server/jobs/         جدولة وإرسال وتنفيذ الأعمال الخلفية
    src/contracts/           عقود المدخلات والمخرجات وأكواد الأخطاء
    src/locales/ar/          الرسائل العربية
    db/migrations/           ترحيلات مرقمة مراجعة
    db/seeds/                بيانات تطوير معزولة
    tests/                   الوحدة والتكامل والمتصفح
    ops/                     التشغيل والنشر والاستعادة
    docs/                    المواصفات والقرارات والتقدم

لا تُنشأ هذه المجلدات جميعًا كقوالب فارغة؛ ينشئ كل تنفيذ ما يحتاجه. تجمع خدمة المجال الكتابة والتدقيق والحدث في معاملة واحدة؛ لا تعيد الواجهة تنفيذ قواعد الرصيد.

## 3. نموذج البيانات

الأسماء التالية عقد تصميم، وتتحول إلى migrations تدريجيًا. لكل كيان دائم معرف داخلي UUID ووقت إنشاء؛ أرقام الدفعات البشرية مستقلة عن المفتاح الداخلي.

| الكيان | أهم البيانات والعلاقات |
|---|---|
| users / sessions | جداول مكتبة المصادقة، وتعطيل المستخدم دون حذف تاريخه |
| user_permissions / assignments | الدور، التفويضات، نطاق العمل، المسؤول الحالي |
| factory_settings | المنطقة الزمنية، بداية الأسبوع، دقة الوزن، إعدادات التنبيه |
| product_types / products | النوع، الكود، الاسم، نشط/معطل، فئة المادة ووحدتها |
| process_recipes / recipe_versions | المنتج المستهدف، مواد الإدخال، تسلسل المراحل والسياسات المعتمدة |
| suppliers / receipts / receipt_lines | مورد، مرجع، received_at، البنود والكميات والوحدات |
| material_lots | مصدر المادة ورقمها وحالتها وروابط الاستلام |
| assets / equipment | بيانات الأصل؛ نوع وسعة وحالة المعدة عند انطباقها |
| fermentations / fermentation_inputs | المنتج المستهدف، نسخة الوصفة، مصادر المواد وكمياتها |
| production_orders | fermentation_id، رقم فرعي، كمية السحب، تواريخ البدء والإكمال |
| stage_runs | مرجع تخمير أو أمر إنتاج، نوع المرحلة، رقم المحاولة، الحالة والكمية والسياسة |
| equipment_allocations | المعدة، stage_run، وقت الحجز والإخلاء، حالة نشطة |
| stoppages | stage_run، السبب، occurred_at، ended_at، end_reason، ended_by، resumed_at للاستئناف الفعلي فقط، actors، أثره على المؤقت |
| quality_reviews | المرحلة/الكمية، سبب الحجز، قرار المسؤول، وقت الاعتماد |
| material_accounts / balance_projections | حساب كمية حسب المادة والدفعة والمرحلة والموقع والحالة والوحدة |
| material_movements / movement_lines | نوع الحركة، حسابات المصدر والوجهة، مقادير دقيقة، المصدر التجاري |
| finished_lots / dispositions | الناتج، أمر المصدر، متاح/محجوز، المخزون أو البيع وكمياتهما |
| sales / sale_lines / returns | مرجع التصريف، الكمية، مصدر مباشر/مخزون، المرتجع وحالته |
| audit_events | الفاعل، الفعل، الكيان، وقت الحدث والتسجيل، الفرق والسبب، request_id |
| idempotency_requests | مفتاح الطلب، الفاعل، العملية، بصمة المدخلات، الحالة والنتيجة |
| outbox_events / scheduled_jobs | حدث محفوظ مع المعاملة، موعد، نسخة الجدولة، محاولات وقفل مؤقت |
| notifications / notification_deliveries | المستلم، الموضوع، القراءة، القناة، محاولات الإرسال ومفتاح منع التكرار |

لـ stage_runs مالك واحد فقط: تخمير أو أمر إنتاج، بقيد XOR. حالات دفعة التخمير منفصلة عن مرحلة معالجتها حتى يمكن إبقاء الرصيد بعد اكتمال المعالجة. أسماء المنتج والوصفة والسياسات تُحفظ بنسخة تاريخية عند الإنشاء؛ تعديلها للمستقبل لا يغير تقارير الماضي.

## 4. الأوزان وحسابات المادة

- تخزن الكميات باستخدام NUMERIC(18,3)، وتنقل JSON كسلاسل عشرية مثل "5000.000". تُرفض دقة زائدة بدل تقريبها بصمت.
- الحساب التجاري على الخادم باستخدام حساب عشري دقيق أو SQL؛ لا استخدام JavaScript Number لتجميع الرصيد.
- الأصول غير الوزنية تستخدم وحدة عددية منفصلة؛ لا جمع أو تحويل بين وحدات غير متوافقة.
- حساب المادة يحدد الصنف والدفعة والمرحلة والموقع والحالة؛ له رصيد لا يصبح سالبًا.
- السجل الحركي أصل الحقيقة. جدول الرصيد projection للتحديث السريع، يتغير داخل المعاملة نفسها ويمكن إعادة بنائه ومطابقته.
- النقل يخرج كمية من حساب ويدخلها في حساب آخر ضمن معاملة. التحويل التصنيعي يربط المدخلات بالمخرجات وفرق المعالجة والعينات والتالف المصنف.
- كيان النظام يسمح بحسابات مصدر استلام ومخرجات معالجة محددة؛ لا يطبق قيد عدم السالب على حساب خارجي افتراضي، بل على أرصدة المصنع الفعلية.
- قاعدة ميزان الكتلة لكل تحويل: المدخلات + الإضافات = الناتج + المتبقي + المخرجات الأخرى + فرق المعالجة. يجب تصنيف الفرق وربطه بسياسة المرحلة.
- الإصدار الأول يعالج كامل رصيد أمر الإنتاج في المرحلة؛ التقسيم التشغيلي يكون عند السحب من التخمير، والتوزيع الجزئي عند تصريف الناتج. هذا يحد الحالات المتفرعة.
- لا يُسمح بإرجاع سحب إلى التخمير بعد بدء معالجته. تصحيح سحب لم يبدأ له حركة عكسية موثقة وتحقيق في الرصيد.

## 5. عقد الكتابة الآمنة

العميل يولد Idempotency-Key للعملية فقط. expected_version هي آخر نسخة أعادها الخادم للمورد الذي يحدده عقد الأمر؛ لا يولدها العميل ولا يزيدها بنفسه. أوامر الإنشاء التي لا تملك موردًا سابقًا لا تحتاج نسخة مختلقة. الأوامر المركبة تحدد الموارد والنسخ المطلوب فحصها، مع بقاء أقفال الرصيد والتحقق داخل المعاملة. عند إعادة طلب مجهول النتيجة يرسل العميل المفتاح والجسم الأصليين دون تغيير النسخة؛ وبعد رفض حاسم ومراجعة المستخدم ينشئ أمرًا جديدًا بمفتاح جديد عند الحاجة.

تسلسل الخدمة:

1. تحقق الجلسة والتفويض على الكيان الفعلي، ثم شكل المدخلات وحدودها.
2. افتح معاملة باستخدام اتصال واحد من pool.
3. احجز سجل idempotency ضمن نطاق الفاعل ونوع العملية والمفتاح؛ إذا كان موجودًا بنفس المدخلات أعد النتيجة السابقة، وإذا اختلفت المدخلات أعد 409.
4. اقفل السجلات المتأثرة بترتيب ثابت؛ مثل رصيد التخمير ثم أمر الإنتاج ثم تخصيص المعدة.
5. تحقق النسخة والحالة والرصيد والسياسة داخل القفل، لا اعتمادًا على قراءة واجهة سابقة.
6. اكتب الحركة وتحديث الرصيد والحالة وأثر التدقيق وoutbox والنتيجة المرجعية.
7. COMMIT ثم أعد النتيجة المعتمدة. أي خطأ قبل ذلك يؤدي إلى ROLLBACK.
8. ينفذ العامل الخلفي الآثار الخارجية بعد الالتزام؛ لا ترسل إشعارًا خارجيًا داخل المعاملة.

في node-postgres يجب استخدام client واحد لكل أوامر المعاملة، وإعادته إلى pool في finally؛ لا توزيع أوامرها عبر pool.query. [التوثيق الرسمي](https://node-postgres.com/features/transactions).

أقفال الصفوف والتحديث المشروط أدوات لمنع تعارض السحب؛ يلزم قفل جميع الأرصدة المتأثرة وقيود مناسبة، لا الاعتماد على اسم مستوى العزل وحده. [أقفال PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

معالجة deadlock/serialization retries محدودة ومع المفتاح نفسه. القفل لا يبقى أثناء انتظار إدخال المستخدم أو شبكة خارجية. لا تنفذ retry عشوائيًا لأخطاء تحقق أو نقص رصيد.

تُحتفظ بصلة المفتاح بالحركة التجارية على المدى الطويل؛ يمكن أرشفة جسم الاستجابة بعد مدة مقررة، لكن لا يجوز نسيان المفتاح بحيث تعاد الحركة القديمة من جديد. إعادة الطلب بعد تغير صلاحية المستخدم تتطلب تحقق الوصول قبل إعادة أي نتيجة.

## 6. قيود وفهارس أولية

- UNIQUE على رقم الدفعة، رقم أمر الإنتاج، (parent_id, sequence_no)، ومفتاح idempotency.
- FK لكل المراجع، CHECK للأوزان غير السالبة والدقة والوحدات وتسلسل الأوقات.
- فهرس فريد جزئي لتوقف مفتوح واحد لكل stage_run، ولمعدة مشغولة واحدة وفق سياسة النسخة الأولى.
- لا يولد رقم الدفعة بـ MAX+1؛ عداد محجوز ذريًا أو sequence مع قيد UNIQUE، ولا حاجة لترقيم بلا فجوات.
- فهارس مركبة حسب الاستعلام: production_orders(status, created_at, id)، movements(account_id, occurred_at, id)، notifications(recipient_id, created_at, id).
- scheduled_jobs(status, due_at, id)، ومفاتيح FK كثيرة الاستخدام، وفهرس للحالات النشطة.
- لا فهرسة كل عمود. تؤكد الحاجة بـ EXPLAIN وبيانات اختبار واقعية، مع مراقبة تكلفة الكتابة.

## 7. عقود API الأولية

كل المسارات أدناه تحت /api/v1. القراءة تعيد حقول العرض الضرورية وserver_time وversion عند الحاجة، والقوائم تعيد next_cursor. الأخطاء منظمة: code، message_key، field_errors، request_id دون stack trace.

| الطريقة والمسار | المدخل الأساسي | الأثر |
|---|---|---|
| GET /products?type_id=... | النوع والبحث والحد | قائمة أصناف النوع |
| POST /receipts | مرجع وبنود كميات ووحدات | استلام وأرصدة مواد |
| POST /fermentations | product_id، quantity_g، مصادر عند التعدد | دفعة ومعالجة تخمير |
| POST /fermentations/:id/ready | نتيجة فحص | إتاحة السحب |
| POST /fermentations/:id/withdrawals | quantity_g، expected_version | أمر إنتاج مستقل وخفض الرصيد |
| POST /stages/:id/start | equipment_id عند الحاجة | تشغيل وحجز المعدة وجدولة |
| POST /stages/:id/pause | reason_code، note عند الحاجة | توقف موثق |
| POST /stages/:id/resume | expected_version | استئناف وفق السياسة |
| POST /stages/:id/complete | output_quantity_g، تفسير استثناء إن وجد | ناتج وانتظار التالية |
| POST /reviews/:id/decision | القرار والسبب | اعتماد/إعادة معالجة/حجز/إتلاف |
| POST /finished-lots/:id/dispositions | تخصيصات كمية ووجهة | مخزون و/أو بيع مباشر |
| POST /stock/sales | الدفعة والكمية والمرجع | بيع من المخزون |
| POST /returns | sale_line_id، quantity_g، سبب | مرتجع محجوز للفحص |
| POST /corrections | مرجع الحركة والسبب والتصحيح | تصحيح بتفويض ومعاملة |
| GET /operations | المرحلة والحالة وcursor | العمليات الحالية |
| GET /reports/:kind | الفترة والتوقيت والمرشحات | التقرير وتعريف نطاقه |
| GET /notifications | cursor | إشعارات المستخدم الحالي |
| POST /notifications/:id/read | معرف الإشعار | علامة قراءة دون حذفه |
| GET /requests/:key | مفتاح طلب للمستخدم المصرح | تحقق من نتيجة حفظ غير مؤكدة |

يُستكمل العقد في T04 بمسارات الأصول والإعدادات والمستخدمين والتفويض والأرصدة والتصدير، وحالات 400/401/403/404/409/422/429/503. 404 لعدم وجود المورد، و403 لعدم الإذن وفق سياسة منع تسريب وجود الكيانات. تُوثق واجهة المصادقة من المكتبة بدل اختراع بديل.

مثال سحب: body يحتوي quantity_g: "5000.000" وexpected_version: 3. النجاح يعيد رقم الأمر الفرعي، remaining_quantity_g: "20000.000"، version: 4 ووقت الخادم. نقص الرصيد يعيد INSUFFICIENT_BALANCE دون أي حركة جزئية.

## 8. استراتيجية جلب البيانات

- أول تحميل للصفحة من الخادم عبر DAL نفسها؛ تحديثات العميل عبر API تستخدم الخدمات نفسها. لا يبني الخادم طلب HTTP لنفسه بلا حاجة.
- جلب الاستعلامات المستقلة بالتوازي، وما يعتمد على نتيجة سابقة بالتسلسل. تقييد عدد الاتصالات والتوازي عند وجود قوائم طويلة.
- قوائم بحد ابتدائي 25 وحد أقصى 100، cursor مستقر على (created_at, id)، وترتيب وأعمدة مسموحة فقط.
- لا SELECT * ولا N+1، ولا تنزيل كل الحركات لحساب تقرير في المتصفح.
- بحث مؤجل 300ms وإلغاء الطلب القديم ومنع نتيجة نوع قديم من استبدال نتيجة النوع الحالي.
- مؤقت مرئي محلي مشتق من وقت الخادم؛ لا طلب كل ثانية.
- تحديث العمليات كل 15 ثانية للشاشة النشطة، والتنبيهات كل 30 ثانية كأهداف أولية قابلة للضبط. تحديث فور نجاح حركة، وعند استعادة التركيز والاتصال.
- تتوقف إعادة الجلب الدورية عند إخفاء الصفحة أو غياب الشبكة؛ SWR يدعم سياسات إعادة التحقق هذه. [مرجع SWR](https://swr.vercel.app/docs/revalidation).
- البداية بلا WebSocket؛ إن لم تكف مدة التحديث لحاجة التشغيل، يُسجل قرار SSE مع قياس التكلفة وإعادة الاتصال.

## 9. التخزين المؤقت والاتساق

| البيانات | السياسة |
|---|---|
| رصيد قبل كتابة | قراءة حديثة داخل المعاملة؛ لا اعتماد على cache |
| عمليات نشطة | بلا cache خادمي مشترك مبدئيًا؛ cache عميل قصير مع تحديث |
| كتالوج الأصناف | cache عميل حتى 5 دقائق مع invalidation عند التعديل |
| تقارير | استعلام مباشر أولًا؛ cache قصير لاحقًا إذا أثبت القياس الحاجة |
| بيانات جلسة أو صلاحية | لا cache عام؛ إبطال عند إلغاء الصلاحية أو الجلسة |

تحتوي مفاتيح cache العميل على هوية/نطاق المستخدم والفلاتر والتوقيت، ويُمسح cache عند الخروج أو تبديل الحساب. استجابات API الخاصة لا توضع في CDN عام. بعد mutation تُحدّث مفاتيح الرصيد والعملية والتقارير المتأثرة؛ التزام قاعدة البيانات مستقل عن نجاح تحديث الشاشة.

## 10. الترحيل والتاريخ

كل تعديل schema بملف migration مرقم ومراجع. اختبار من قاعدة فارغة ومن النسخة السابقة. فصل صلاحيات migration عن مستخدم التطبيق. بيانات الافتتاح تدخل كحركات opening_balance بتاريخ وسبب واعتماد، لا بتعديل حقل رصيد مباشرة.

التوقيت TIMESTAMPTZ مع تخزين اللحظات وتمثيلها بتوقيت المصنع. لكل حدث occurred_at وrecorded_at؛ الافتراضي وقت الخادم، والتسجيل الرجعي تصحيح محدود الصلاحية يُراجع تأثيره على الأحداث التالية والتقارير.

التصدير يعالج النصوص التي قد تُفسر كصيغ في برامج الجداول، ويطبق نفس صلاحيات الواجهة. المرفقات الخاصة عبر روابط محدودة المدة، وحد حجم ونوع، ولا تُعرض مباشرة كملفات عامة.
