# الجودة والأمان والموارد والحفظ التشغيلي

## 1. استراتيجية التحقق

اختبارات الوحدة لقواعد الزمن والوزن وانتقالات الحالات والفترات؛ اختبارات تكامل PostgreSQL للمعاملات والقيود والتزامن؛ اختبارات متصفح للمسارات الأساسية والعربية والصلاحيات الظاهرة. لا تكفي mocks لاختبار الأقفال أو عزل المعاملات.

الوقت في الاختبارات قابل للتحكم. لا ننتظر 7 أيام لتجربة التخمير؛ نستخدم ساعة اختبار، مع بقاء المصدر الحقيقي في الإنتاج وقت الخادم الموثوق.

كل تغيير يمر بفحص الأنواع وبناء مناسب واختبارات السلوك المتأثر. CI يشغل الاختبارات الآلية اللازمة، وقبل الإطلاق تشغيل شامل للسيناريوهات الحرجة. يُسجل الأمر والنتيجة والبيئة، ولا تسجل عبارة «ناجح» دون دليل.

## 2. مصفوفة قبول أساسية

| الحالة | النتيجة المتوقعة |
|---|---|
| النوع A ثم اختيار B | قائمة B فقط والمنتج السابق يُمسح |
| استلام 25,000 ثم تخميرها | الخام ينخفض 25,000 والتخمير يرتفع 25,000 |
| سحبان 5,000 و4,000 | أمران مستقلان، المتبقي 16,000 |
| سحبان متزامنان 4,000 لكل منهما من رصيد 5,000 | واحد فقط ينجح، رصيد 1,000 |
| تكرار الطلب بنفس المفتاح | نفس الأثر التجاري مرة واحدة |
| نفس المفتاح مع جسم مختلف | 409 دون كتابة جديدة |
| COMMIT نجح والرد فُقد | استعلام/إعادة محاولة يعيدان النتيجة دون تكرار |
| فشل بين خفض الرصيد وإنشاء الأمر | rollback كامل |
| انتهاء مؤقت | طلب فحص، لا إكمال ولا نقل تلقائي |
| توقف active_time ثم استئناف | تحديث الموعد مع حفظ التاريخ |
| توقف elapsed_time | الموعد لا يتجمد |
| توقف بعد التأخر | سجل التأخر لا يختفي |
| إعادة تشغيل worker أو عاملان | لا فقد وظيفة، ولا إشعار داخلي مكرر |
| وظيفة قديمة بعد تعديل المدة | تُتجاهل بناء على schedule_version |
| تشغيلان على معدة واحدة محجوزة | الثاني يُرفض دون حالة جزئية |
| رفض/تالف كامل | كمية مصيرها معروف والناتج صفر مع اعتماد |
| إعادة معالجة | محاولة جديدة دون مضاعفة المخزون أو مدخل الناتج |
| تصريف 3,400 إلى 2,400 مخزون و1,000 بيع | الرصيد النهائي بانتظار التصريف صفر |
| بيع 400 من المخزون ثم مرتجع 100 | المتاح 2,000 والمحجوز 100 حتى قرار الفحص |
| عامل يستدعي تقرير مدير مباشرة | رفض وصول دون تسريب بيانات |
| فتح حساب آخر على الجهاز | لا تظهر بيانات cache الحساب السابق |
| تقرير دفعات عابرة للشهر | حركة الفترة والناتج المرتبط منفصلان وصحيحان |
| استعادة نسخة | الحسابات والأرصدة والعلاقات والمرفقات متطابقة ضمن نقطة الاستعادة |

تضاف اختبارات الحدود: رقم عربي، دقة زائدة، كمية سالبة، تاريخ مستقبلي غير مسموح، رقم دفعة فريد، ناتج أكبر من الداخل بلا إضافة معتمدة، ومعرّف مورد لا يخص العملية.

## 3. الأمان دون تعقيد على العامل

- مصادقة بمكتبة معتمدة؛ لا بناء hashing أو session crypto يدويًا. لا تسجيل عام ولا حسابات مشتركة.
- التحقق من الجلسة والدور ونطاق الكيان في خدمة كل طلب، لا الاكتفاء بإخفاء زر.
- جلسات في cookies آمنة HttpOnly وSecure وسياسة SameSite مناسبة؛ حماية CSRF والتحقق من Origin للكتابة حسب تكامل المكتبة، واختبارها.
- كلمات المرور والمفاتيح في إدارة أسرار البيئة؛ لا في Git ولا بيانات العرض أو سجلات الطلبات.
- SQL بمعاملات قيم ثابتة، وأسماء أعمدة الترتيب من allowlist، وحدود للصفحات والطلبات وحجم النصوص والملفات.
- rate limits للدخول والكتابة المكثفة والتصدير، مع رسائل مفهومة. إعادة محاولة عملية مالية/كمية مرتبطة بـ idempotency.
- تشفير اتصال الويب وDB حين تعبر الشبكة، وقاعدة غير مكشوفة للعامة.
- مستخدم تطبيق دون superuser، ومستخدم migrations منفصل؛ لا permission UPDATE/DELETE لسجل الحركات المعتمد عبر الدور الاعتيادي.
- audit log يوضح الفاعل والتصحيح، لكنه ليس محصنًا من مدير قاعدة بصلاحيات كاملة؛ تُقيد هذه الصلاحيات وتراقب وتنسخ السجلات خارج البيئة عند الحاجة.
- النصوص المعروضة تُهرب، ورسائل الاستثناء الداخلية لا تعرض للعامل. لا إرسال بيانات المصنع إلى خدمة خارجية دون ضرورة معتمدة.
- مصادقة متعددة العوامل للمالك/المدير مقترحة، مع وسيلة استرداد عملية؛ لا تُفرض خطوة إضافية على كل حركة عامل.

## 4. ميزانية الأداء والموارد

الأرقام التالية أهداف أولية للقياس في T25، وليست وعدًا أو توصية شراء. تُراجع بعد معرفة عدد المستخدمين والمعدات وحجم البيانات والاستضافة.

| البند | هدف أولي |
|---|---|
| حمل اختبار | 20 مستخدمًا متزامنًا، و100,000 أمر و1,000,000 سطر حركة اصطناعي |
| قراءة شاشة تشغيل | p95 أقل من 500ms لزمن API في بيئة الاختبار الموثقة |
| حركة حفظ عادية | p95 أقل من 1 ثانية دون تأخير شبكة المستخدم |
| تقرير اعتيادي | أقل من ثانيتين؛ التصدير الكبير مهمة خلفية |
| تأخر إنشاء تنبيه مستحق | أقل من 60 ثانية أثناء سلامة الخدمات |
| تحديث الشاشة النشطة | عمليات 15 ثانية، تنبيهات 30 ثانية، وتحديث بعد الإجراء |
| الجلب | 25 سجلًا افتراضيًا، 100 كحد أقصى لكل صفحة |
| استهلاك أولي للتجربة | ويب حتى 2 vCPU و2GB، worker حتى 1 vCPU و512MB، DB حتى 2 vCPU و4GB؛ تُقاس كفايتها |

تُختبر الأهداف على جهاز/استضافة معلومة، وتُسجل الذاكرة والاتصالات وقرص DB ونموه والاستعلامات البطيئة وأعمار المهام. تحديد أسعار أو مزود استضافة يُترك لقرار بنية ببيانات فعلية، ولا يشتري المنفذ اشتراكًا تلقائيًا.

قواعد الاقتصاد:

1. مؤقت عرض محلي؛ لا كتابة أو قراءة DB كل ثانية لكل عملية.
2. لا تنزيل صور كبيرة أو مكتبات رسوم على شاشة العامل؛ تحمل الرسوم عند فتح الإدارة.
3. تجميع تقارير SQL وفهارس مختارة؛ لا N+1 ولا SELECT *.
4. pool اتصالات بحدود محسوبة لمجموع نسخ الويب والعامل، مع هامش للإدارة والنسخ. نقطة بداية 10 للويب و3 للعامل تُراجع مقابل حد DB.
5. مهام تصدير محدودة التزامن والحجم والوقت، retry بحدود وbackoff، وقياس backlog.
6. لا نسخ احتياطي على القرص نفسه فقط، ولا تخزين ملفات ضخمة في صفوف DB.
7. autovacuum ومراقبة نمو الجداول؛ لا VACUUM FULL أو REINDEX دوري عشوائي يوقف المصنع.
8. تقليل تكاليف التطوير بإعادة استخدام المكونات والمواصفات وتنفيذ مهمة صغيرة في كل دورة Gemini.
9. إضافة cache أو read replica أو partitioning فقط بعد دليل اختناق وقرار تكلفة/صيانة.

## 5. النسخ الاحتياطي وحماية البيانات

الهدف المقترح قبل اعتماد المصنع: RPO لا يزيد على 15 دقيقة، وRTO لا يزيد على 4 ساعات. RPO يعني أقصى نافذة فقد مقبولة، وRTO أقصى زمن استعادة مستهدف. كلاهما يحتاج تنفيذًا وقياسًا فعليًا.

نسخة يومية وحدها لا تحقق RPO 15 دقيقة. لتحقيق الهدف نحتاج نسخًا أساسية مع أرشفة WAL/PITR أو خدمة مكافئة، ومراقبة فعلية لتأخر الأرشفة. أساليب النسخ مختلفة ولها متطلبات استعادة؛ يُراجع التوثيق المناسب للإصدار والمزود. [نسخ PostgreSQL](https://www.postgresql.org/docs/current/backup.html).

سياسة مقترحة: نسخ يومية محفوظة 30 يومًا، ونافذة استعادة زمنية 14 يومًا مع نسخ أساسية صالحة لها، ونسخة دورية خارج حساب/بيئة التشغيل. الاحتفاظ النهائي وفق سياسة صاحب المصنع وتكلفة التخزين، ولا حذف لسجلات العمل تلقائيًا بمجرد بلوغها عمرًا محددًا.

تُشفر النسخ وتقيد صلاحياتها، وتُحفظ مفاتيح استعادتها خارج الخادم المصدر بطريقة يمكن للمسؤول الوصول إليها. إن وجدت مرفقات تُنسخ بإصداراتها ويُحفظ تطابقها مع مراجع DB. إعدادات النشر والأسرار لها إجراء استرداد مستقل؛ لا نضع الأسرار داخل مستودع التوثيق.

## 6. إجراء الاستعادة

1. حدد سبب الحادث ونقطة الاستعادة المطلوبة، وأوقف الكتابة المتأثرة عند الضرورة.
2. احفظ دليل الحادث ونسخة من الحالة الحالية إن أمكن؛ لا تكتب فوق المصدر قبل التحقق.
3. استعد إلى بيئة معزولة من النسخة الأساسية وWAL أو آلية المزود.
4. تحقق من schema والمستخدمين وأعداد السجلات والعلاقات ومطابقة ledger/balances وعينات الدفعات.
5. تحقق من المرفقات إن وجدت ومن حسابات الدخول دون كشفها.
6. قبل تشغيل worker، راجع الوظائف القديمة والمدفوعات/المبيعات الخارجية إن وجدت؛ امنع إرسال تنبيهات متقادمة أو تكرار أثر حدث نُفذ خارج النسخة المستعادة.
7. صالح الحركات التي حدثت بعد نقطة الاستعادة مع سجل التشغيل الواقعي، وسجل أي فقد صراحة.
8. وثق زمن الاستعادة والنقطة الفعلية وحدود الفقد، ثم حوّل الخدمة بعد اعتماد المسؤول.

تُجرى تجربة استعادة قبل الإطلاق ثم دوريًا، مثل شهريًا في البداية، وتُعدل الدورية حسب الحاجة. نجاح إنشاء ملف backup لا يساوي نجاح الاستعادة.

## 7. النشر والترقيات

بيئات منفصلة للتطوير والاختبار وstaging والإنتاج. أي بيانات مصنع مستخدمة في اختبار تُختزل أو تُنقح، ولا تنسخ إلى بيئة عامة.

المسار: تثبيت مقفل → check/tests/build → نشر staging → تجربة smoke → نسخة/نقطة استعادة → migrations مراجعة → نشر ويب وعامل متوافقين → فحص صحة وتشغيل بسيط → مراقبة.

ترحيل schema يتبع expand/migrate/contract إذا كانت البيانات الحية تحتاج ذلك. لا يُحذف عمود قبل انتقال جميع القراءات والكتابات. rollback التطبيق لا يعني rollback البيانات تلقائيًا؛ يُفضل إصلاح أمامي أو إصدار متوافق، مع خطة خاصة لأي migration تدميرية.

المنصة المختارة يجب أن تدعم worker دائمًا أو مجدولًا بتواتر يفي بهدف التنبيه. لا تعتمد جدولة مصنع على طلبات الزوار أو بيئة قد تُطفئ العملية الخلفية دون إشراف.

## 8. المراقبة والتعامل مع الانقطاع

مؤشرات: أخطاء API، زمن الاستجابة، اتصالات DB، مساحة القرص، lock waits، استعلامات بطيئة، عمر أقدم مهمة، heartbeat العامل، فشل إرسال متكرر، آخر نسخة ناجحة وتأخر WAL.

تنبيه فشل النسخ أو العامل يذهب إلى قناة تشغيل مستقلة قدر الإمكان؛ إذا كانت الخدمة معطلة لا يكفي وضع تنبيه داخل التطبيق نفسه.

في انقطاع الشبكة: لا يُعتبر العمل الفيزيائي متوقفًا تلقائيًا. يمكن متابعة إجراءات المصنع المعتمدة مع سجل بديل مبسط: رقم الأمر، الحدث، الوقت الحقيقي، الوزن، العامل. بعد عودة الخدمة يدخل مسؤول مخول الأحداث مع occurred_at وrecorded_at وسبب التأخر، ويُراجع تعارضها مع الأحداث الموجودة قبل اعتمادها.

نسخة الإصدار الأول لا تتيح كتابة مخزون دون اتصال. يمكن عرض بيانات سبق تحميلها مع علامة قدمها، لكنها ليست ضمانًا لصحتها الحالية. دعم مزامنة offline آمنة مرحلة لاحقة تحتاج حل تعارض مستقلًا.

## 9. جاهزية الإطلاق والتسليم

- اعتماد قرارات المواد والمراحل والتوقيت والتوقف والمعدات والتعبئة والبيع والنسخ والتنبيه.
- إدخال أصناف ومعدات ومستخدمين وأرصدة افتتاحية موثقة؛ لا حسابات تجريبية في الإنتاج.
- تدريب العامل على البدء والوزن والتوقف والاستئناف وفشل الحفظ، وتدريب المدير على الحجز والتصحيح والتقارير.
- اختبار بيانات المصنع في دورة محدودة ومطابقة الأوزان الفعلية مع النظام.
- تحديد من يدير الاستضافة والنسخ والاستعادة والأذونات والدعم، وكيف يتواصل معه المصنع.
- وجود دليل مختصر للعامل ودليل استثناءات للمدير ودليل استعادة للمشغل.
- جميع عيوب سلامة البيانات مغلقة، ونتائج القياس والاختبارات متاحة.

ملفات التطبيق والتشغيل لا تصبح مكتملة بمجرد اكتمال هذه الخطة؛ ينفذها المساعد ضمن T03–T30 ويثبت الأدلة في سجل التقدم.
